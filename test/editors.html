Editor behaviour fixtures

These reproduce the two ways a naive restore fails. Both failures look like success for a second or two, which is what makes them worth a test.

1. A framework-controlled input

Reproduces React's value tracking: a getter/setter pair on the element instance, plus a private record of the last value the framework knows about. An input event whose value equals that record is treated as "nothing changed" and dropped.

2. A model-driven rich editor

Reproduces how Lexical, ProseMirror, Slate and Draft.js work: the editor keeps its own document model, updates it from beforeinput/input, and reconciles the DOM from the model whenever it re-renders. A DOM write it never saw is discarded at the next render.

3. A plain contenteditable

No model, no framework. Here to check one property in isolation: a restore has to be undoable with Ctrl+Z. The editors above cannot show this, because their re-render writes to the DOM directly and that write is invisible to the browser's own undo stack.
